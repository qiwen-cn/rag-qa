# 技术文档：从 Python 到 AI —— 大语言模型的底层原理与工程实践


## 第一章：Python 为什么能统治 AI 时代？

在当今的人工智能领域，Python 已经成为了无可争议的“母语”。无论是学术界的顶级论文，还是工业界的落地应用，Python 都占据着绝对的主导地位。这并非偶然，而是由其语言特性和历史机遇共同决定的。

首先，Python 拥有极其繁荣的第三方生态。在 AI 领域，NumPy 负责基础的多维数组计算，Pandas 负责数据清洗与分析，PyTorch 和 TensorFlow 则统治了深度学习的框架层。这些底层库通常用 C++ 编写以保证极致的计算性能，但通过 Python 提供极其友好的接口。这种“底层高效运行，上层轻松调用”的设计，让开发者能将精力集中在业务逻辑上。

其次，Python 的胶水语言特性使其能轻易地与其他语言融合。在 AI 推理阶段，通常需要将模型部署到 C++、Rust 或 Go 编写的微服务中。Python 可以作为连接数据处理与模型部署的桥梁。

然而，Python 并非没有缺点。其最显著的短板是全局解释器锁（GIL）。GIL 导致在多核 CPU 环境下，Python 的多线程无法实现真正的并行计算。对于计算密集型的任务，开发者通常只能使用多进程，这带来了额外的内存开销。尽管如此，由于 AI 的核心计算（矩阵运算）已由底层 C++ 库或 GPU 接管，GIL 对 AI 训练和推理的负面影响被降到了最低。


## 第二章：大语言模型（LLM）的“思考”机制

大语言模型（Large Language Model，简称 LLM）的爆发，标志着 AI 从“判别式”走向了“生成式”。要理解大模型，我们需要了解三个核心概念：Token、Transformer 架构、以及自注意力机制。

### 1. 什么是 Token？

计算机无法直接理解人类的自然语言（汉字、英文单词）。Token 是模型处理文本的最小单位。不同模型的分词器不一样，一个汉字通常对应 1 到 2 个 Token，一个英文单词通常是 1 个 Token。例如，“我爱 Python”可能被切割成 ["我", "爱", "Py", "thon"] 四个 Token。模型实际上是在计算下一个 Token 出现的概率，从而逐字生成回答。

### 2. Transformer 架构与自注意力机制（Self-Attention）

2017 年，Google 团队发表了一篇名为《Attention Is All You Need》的论文，彻底改变了 NLP（自然语言处理）的格局。Transformer 架构的核心是自注意力机制。

在传统的循环神经网络（RNN）中，句子必须从左到右依次处理，不仅速度慢，而且容易忘记前文的上下文。而自注意力机制允许模型在处理某个词时，同时“看”到句子中的其他所有词，并计算它们之间的关联权重。

例如，在句子“苹果公司发布了新款手机，它非常昂贵”中，自注意力机制会自动将“它”与“手机”关联起来，赋予极高的权重，从而理解“它”指代的是“手机”而不是“苹果”。

### 3. 大模型的两大缺陷：幻觉与知识时效性

目前的大模型（如 DeepSeek、ChatGPT）主要依靠预训练（Pre-training）获得知识。这意味着它们的能力被冻结在了训练数据截止的那一天。

当用户询问训练数据之后发生的事情，或者询问极其冷门的专业细节时，大模型往往会产生“幻觉”（Hallucination）。即模型会一本正经地“胡说八道”，编造看似合理但完全虚假的事实。这是目前大模型在企业落地中面临的最大挑战。


## 第三章：RAG（检索增强生成）技术与溯源

为了解决幻觉和时效性问题，工程界提出了 RAG（Retrieval-Augmented Generation，检索增强生成）技术。这也是文档问答应用的底层逻辑。

RAG 的核心思想是：不要让模型去“背”答案，而是让模型去“开卷考试”。

RAG 的流程通常分为三步：

1. **文档切分（Chunking）**：将长文档切分成若干个短小的段落（Chunk）。
2. **向量化与检索（Retrieval）**：利用 Embedding 模型将用户的提问和所有段落转化为向量（多维数字数组）。通过计算向量之间的余弦相似度，找出与用户问题最相关的 3 到 5 个段落。
3. **生成（Generation）**：将用户的问题和检索到的这几个段落一起拼接成 Prompt，发送给大模型，要求大模型“仅根据提供的段落回答问题，并指明依据出处”。

通过 RAG 技术，不仅解决了模型知识时效性问题，还大幅度降低了成本。因为不需要重新训练模型，只需更新检索库即可。


## 第四章：基于 FastAPI 与 DeepSeek 的工程实践

在前端与后端的交互中，我们通常采用前后端分离的架构。这里推荐使用 FastAPI 作为后端框架。

FastAPI 是一个现代、高性能的 Python Web 框架。它基于 Starlette（用于网络路由）和 Pydantic（用于数据验证）。FastAPI 的最大特点是原生支持异步（Async/Await）和自动生成 API 文档（Swagger UI）。

在调用大模型（如 DeepSeek）时，开发者需要注意以下工程细节：

**网络超时（Timeout）**：由于生成式接口是逐个 Token 往外吐，一个千字长文的总结可能需要 30 到 60 秒。因此，在客户端发起请求时，Timeout 绝对不能设置为默认的几秒，必须设为 60 秒或更长。

**错误处理**：大模型上游服务可能会因为并发过高、网络抖动或欠费而报错。后端代码必须使用 try...except 捕捉异常，并使用 HTTPException 返回规范的 JSON 错误信息，绝对不要把上游的原始报错直接透传给前端，以免暴露内部细节或导致前端解析崩溃。

**跨域资源共享（CORS）**：仅当前端页面和后端服务不在同一个域名或端口下时，浏览器才会触发同源策略拦截，此时才需要给 FastAPI 引入 CORSMiddleware 中间件。如果前后端同源——例如 HTML 页面本身就由 FastAPI 通过 FileResponse 返回——则完全不需要配置 CORS。确需配置时，也应避免使用 allow_origins=["*"]，那等于允许任意网站调用你的接口，应当明确列出允许的来源。


## 第五章：本项目的具体配置

以下是团队内部约定的参数，未对外公开：

- 文档切分的最小段落长度：20 个字符
- 每次检索返回的段落数量：3 段
- 大模型调用的超时时间：90 秒
- 检索打分使用字符命中次数，不使用向量检索
- 问答接口路径为 /ask，返回字段为 answer 和 sources
- 测试文档的文件名为 doc.txt
